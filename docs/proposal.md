# Proposal: AI 儿童创意游戏平台（AI Kid Games）

## 文档规范

本项目所有正式文档统一存放在项目根目录下的 `docs/` 目录内。

文档存放规则：
- `proposal.md`、`design`、`uat` 以及未来新生成的正式文档，均必须放在 `docs/` 目录内。
- `design`、`uat` 及后续文档如果仅用于特定版本，文件名必须包含版本号。
  - 示例：`design-v1.0.md`
  - 示例：`uat-v1.0.md`

- 项目根目录下必须创建 `temp/` 子目录。
- 项目过程中产生的各种临时文件，包括临时代码、测试报告、调试输出、实验文件等，均必须放在 `temp/` 目录内。
- `temp/` 内临时文件必须按版本号划分子目录。
  - 示例：`temp/v1.0/`

## Why（背景和目标）

### 市场背景

当前 AI 互动内容赛道（Aippy、Loopit 等）聚焦于 15-25 岁欧美 Gen Z 用户，以 AI 生成小游戏 + UGC 社区为核心模式。国内市场在 **3-10 岁儿童 + AI 创意游戏** 方向几乎空白——少儿编程产品（编程猫、核桃编程）偏「教编程」而非「用 AI 创作」，且面向 6 岁以上儿童。

### 用户痛点

- **家长焦虑**：AI 时代来临，不知如何让孩子安全、有效地接触和了解 AI
- **儿童需求**：3-10 岁孩子有强烈的表达欲和创造欲，但缺乏适合年龄的创作工具
- **教培机构痛点**：传统画画/乐高/STEM 机构缺乏 AI 特色课程，难以差异化竞争

### 项目目标

构建一个面向中国 3-10 岁儿童的 AI 创意游戏平台，让孩子通过**语音输入**让 AI 生成可交互小游戏，培养对 AI 的兴趣和基础认知。长期通过**线下地推**进入幼儿园和教培机构，以 **B 端 SaaS + C 端课程**实现商业化。

### 当前阶段策略（2026-10 更新）

长期愿景不变，但当前阶段的优先级调整为“先把产品做‘好’，再把产品做‘大’”：

1. **先服务家庭自用**：以“家庭单机 AI 游戏机”为目标，把儿童生成游戏的核心体验做到最好；暂不引入账号、云端、社区、商业化。
2. **再亲友圈**：在家人/亲友的白名单内验证“作品可见、互相 Remix、共同打磨”。
3. **再公开社区**：在未成年保护、内容安全、云端账号成熟后，再评估公开社区。
4. **商业化暂缓**：广告、付费、B 端 SaaS、微信小程序、原生 App 暂不考虑。

## How（开发方式）

本项目采用 AI-Native 开发方式：
1. 由我制定项目企划书 `docs/proposal.md`
2. AI 根据企划书生成带版本号的 Design 和 UAT 文档，例如：
   - `docs/design-v1.0.md`
   - `docs/uat-v1.0.md`
3. 我确认 Design 和 UAT 后，AI 自行完成：**开发 → 测试 → 修复 → 测试 → 验收通过** 的全流程
4. 在必要的决策环节，AI 需向我确认后再继续
5. 开发过程中的临时文件、测试报告、实验代码等，必须放入对应版本的 `temp/` 子目录，例如 `temp/v1.0/`

## Who（用户故事）

- 作为 3-10 岁的儿童，我希望对着手机说出我的想法（如"我想做一个打地鼠游戏，地鼠是小兔子"），AI 就能帮我生成一个可以玩的小游戏，让我体验创造的乐趣。
- 作为家长，我希望有一个安全的平台让孩子接触 AI，能控制使用时长，看到孩子的创作成果，了解孩子的兴趣发展。
- 作为孩子的家人/亲友，我希望在亲友圈里看到孩子的作品，并能一起 Remix、互相分享。
- （远期）作为幼儿园/教培机构的老师，我希望有一个 AI 启蒙教学工具，能批量管理学生账号、分发创作任务、查看学生作品，提升机构的科技特色竞争力。

## What（功能范围）

### 本次包含（V1.0）

实现MVP，达到能用的效果。
- [x] 基于 Vite + React 的 H5 项目骨架，支持 PC + 手机 Web
- [x] 独立后端 API 服务（AI 生成、作品管理），双模式：Vercel Serverless（`api/`）+ 本地开发（`server/`）
- [x] 首页：面向儿童的简洁入口，大图标 + 语音引导
- [x] 语音输入页面：儿童按住说话 → AI 解析创意 → 生成可交互小游戏
- [x] 游戏模板库：预设 5-10 个主题模板（动物、汽车、公主、恐龙、太空等），降低创作门槛
- [x] AI 游戏生成：调用大模型 API，根据儿童语音描述生成简单可交互的 HTML5 游戏
- [x] 游戏播放器：在 App 内运行 AI 生成的游戏（H5 用 iframe 沙箱）
- [x] 作品列表页：展示该设备上生成过的游戏作品，支持回放和删除
- [x] 家长控制入口：简易的时长设置和作品管理（极简版）
- [x] PC 和手机 Web 端均可运行，响应式适配（极简版）

复盘：
1. 调用火山方舟的大模型花了不少调试时间才理解火山方舟后台的功能
2. 目前只能调用豆包大模型，deepseek，glm 调用的时候还存在问题
3. 虽然设置了5分钟等待时间，但太复杂的游戏，返回失败率偏高

- [x] Remix Prompt 组装：拼接原始 userPrompt + Remix 指令发给 AI，生成新游戏

2. Remix输入的提示词依然比较简单，模型可发挥空间大，输出游戏的精准度太低

目标：Web 端（首页）可以选择模型；未选择时按环境变量 `GAME_MODEL` 配置的模型执行；同时在设置中支持模型的添加、删除、修改、测试。

- [x] 模型配置入口：设置 → 模型配置，必须通过家长验证后进入；支持添加、编辑、删除自定义模型

- [x] 模型测试：内置模型和自定义模型均可一键测试，**仅验证配置的模型参数能否正确完成调用并返回文本**，不生成游戏、不消耗作品记录
- [x] 自定义模型调用：生成接口支持 `modelId`（内置模型）和 `modelConfig`（自定义模型）两种入参
- [x] 模型使用记录：作品保存实际使用的模型 ID/名称，作品列表展示
- [x] 高级配置预留：设置 → 模型配置中预留「提示词优化」「最长提示词」「最长等待时间」配置入口，V4.x 再开放，本版本不生效

#### V3.3 Remix 上下文增强（已完成）

目标：让 Remix **真正基于已经生成的游戏做增量修改**，而不是只拿一句改编指令重新生成一个「面目全非」的新游戏。

- [x] 完整源码上下文：Remix 时把原游戏完整 HTML 源码（受预算约束）随请求发送并注入 Prompt，不再只传 300 字符预览
- [x] 游戏档案注入：服务端从原游戏源码自动提取并注入标题、主题类型、渲染方式、核心机制、交互方式、得分/胜负条件、移动端适配、音效标注等结构信息
- [x] Remix 专用 System Prompt：明确「本次是修改已有游戏，不是从零创作」，强制保留原游戏类型、核心玩法循环、计分/胜负规则、主要交互和美术风格，只做用户要求的最小必要修改
- [x] 源码预算与降级：按字符预算选择「完整源码」或「结构摘要 + 关键代码片段」模式，源码过长时不盲目截断导致模型重写；两种模式的保真要求一致
- [x] 改编结果审计：生成后对比原游戏与新游戏的结构特征，记录渲染方式、交互、得分、胜负是否保留，并在作品元数据中保存
- [x] AI 不可用兜底：Remix 时模型不可用或未配置模型，直接返回原游戏并提示「已保留原游戏」，不再降级为与原作无关的 Mock 游戏
- [x] 前端上下文透传：播放页 Remix 弹窗展示原游戏标题和「将保留」的结构标签，确认后透传完整 HTML、原 Prompt、原标题、模板 ID
- [x] Remix 元数据留存：作品记录 `remixFromTitle`、`remixMode`、`remixProfile`、`remixAudit`，作品列表和播放页展示改编来源与「已保留原玩法」标识
- [x] 兼容约束：旧作品、旧 Remix 请求（仅带 300 字符预览）仍可工作；普通（非 Remix）生成流程与 V3.1 System Prompt 保持不变

本次 V3.3 不包含：
- 基于 diff / patch 的代码级局部编辑（仍要求模型输出完整 HTML，V4.x 之后再评估）
- 多轮对话式 Remix 编辑（顺延至 V4.1）
- Remix 结果与原游戏的逐行 diff 展示
- 模板提示词结构化（移入 V4.0）
- 服务端作品存储与 Remix 谱系云端同步（依赖 V5.1）

复盘：
1. 只把原游戏 HTML 从 300 字符预览改成完整源码，Remix 保真度就发生了质变；真实模型验证中，改编结果保留了原渲染方式、点击交互、得分与胜负，同时正确实现了「宝石 + 炸弹」指令。
2. 结构档案（标题/类型/交互/机制/得分/胜负）比单纯塞源码更能约束模型，也便于生成后做自动化审计。
3. 模型不可用时「保留原游戏」比降级到无关 Mock 更符合用户预期；前端也不再产生重复作品。
4. 源码预算 32,000 字符 + 16,384 输出上限覆盖当前项目绝大多数游戏；超长源码进入摘要模式，但保真度会下降，后续可评估 patch 式编辑。
5. 发现并修复了环境变量空值被当作 0、普通生成响应多出 `remixAudit: null`、旧客户端 preview 未透传等问题，均已加入回归用例。

已拍板决策：

1. 导出/导入放在 Settings（家长验证后）。新增受控入口，不改主流程与路由，视为「不改 UX」。
2. 备份包含自定义模型 API Key。Settings 明确提示「仅保存在自己的设备」，下载不经过服务端。
3. 配置外置由开发者改 `shared/config/*.ts` 后重新构建；不提供界面编辑。
4. Telemetry 只做本地环形缓冲（200 条）+ 手动导出，不上报服务端。
5. 旧作品保留原 ID；仅新作品使用 UUID v4。

本次 V3.6 不包含：
- 界面内编辑配置（Prompt / 模板 / 模型）
- 服务端 telemetry、上报与面板（面板顺延 V4.4）
- 云端存储、账号、跨设备同步（V5.1）
- 修改生成 Prompt 语义、模型路由或降级策略（V4.0 / V4.4）
- 删除或重写旧数据（只做规范化与补默认字段）

复盘：
1. 配置外置的难点不在「抽文件」，而在三端构建：前端 Vite、Vercel `api/` esbuild、本地 `server/` tsc 必须消费同一份配置；最终把 `server/` 的 `rootDir` 放宽到项目根，让 `shared/` 同时进两份产物。
2. 备份包含 API Key 是明确取舍：它让「换设备恢复」真正可用，但把保管责任交给家长；因此 UI 提示、文件名去敏、不写日志三者缺一不可。
3. 导入默认合并、覆盖需二次确认，比「直接替换」更符合家庭场景；旧作品 ID 原样保留，避免旧链接与 Remix 来源失效。
4. Telemetry 只记录枚举、ID、耗时与截断消息，证明「本地可观测」不必以内容上传为代价；V4.4 面板可直接消费同一 schema。
5. V5.1 迁移先落纯函数与 CLI，不提前造云端接口；迁移产物剔除 API Key，避免把本地密钥带进云端。

## 技术约束

### 前端

- 框架：Vite + React 18（JavaScript + 少量 TypeScript）
- 路由：React Router v6（BrowserRouter）
- 样式：普通 CSS 文件，明亮、多彩、圆角、大字体，适合儿童审美
- 目标平台：V3.x–V4.x → H5（PC + 手机 Web）；微信小程序、原生 App 暂不考虑
- 构建工具：Vite
- 部署：Vercel（静态站点 + Serverless Functions）

### 后端

- 运行时：Node.js
- 框架：Hono（轻量，支持 Vercel Functions / 本地 Node.js 服务）
- 语言：TypeScript（严格模式）
- AI 生成：调用 OpenAI 兼容的 Chat Completions API（火山方舟 Ark，支持 Doubao Seed 2.0 Pro、DeepSeek 等模型，可扩展自定义 endpoint）
- 默认模型：通过环境变量 `GAME_MODEL` 指定；内置模型由 `VOLCENGINE_API_KEY`、`DOUBAO_ENDPOINT_ID`、`DEEPSEEK_ENDPOINT_ID` 提供，接口地址可用 `VOLCENGINE_BASE_URL` 覆盖
- 自定义模型：由 Web 端家长验证后管理，保存在浏览器 `localStorage`，生成/测试时随请求提交；服务端不做持久化
- 模型安全：自定义接口地址必须通过域名白名单校验（`ALLOWED_MODEL_HOSTS`），测试接口设置独立超时，API Key 不落日志、不回显
- 语音识别：V3.x–V4.x 继续使用浏览器 Web Speech API；后端语音识别在 V5 再评估
- 存储：V3.x–V4.x 前端 localStorage；V5.1 起迁移到云存储
- 部署：Vercel Functions（生产环境 `api/` 目录）+ 本地 `server/` 开发服务

### 架构原则

- **前后端分离**：前端只做 UI 和交互，核心逻辑（AI 生成、语音识别、内容审核）全部在后端
- **一套 API，单端起步**：当前只服务 H5，未来多端复用同一套 API；不为未发生的多端提前设计
- **渐进增强**：V3.x 内在品质 → V4.x 体验 → V5.x 平台 → V6.x 社区；每个阶段只解决一个命题
- **双后端模式**：Vercel 部署用 `api/`（Serverless），本地开发用 `server/`（独立 Hono 服务）；V3.5 起业务逻辑只在 `server/src/**` 实现，`api/` 由构建脚本打包生成，双端一致性由契约测试锁定

## 设计原则

- **儿童优先**：所有交互必须适合 3-10 岁儿童，大按钮、少文字、多彩色
- **安全第一**：AI 生成内容必须在沙箱中运行；V3.x–V4.x 先保证家庭使用安全，V5.0 起补齐内容审核
- **语音为主**：核心创作流程以语音交互为主，文字输入为辅助
- **即时反馈**：AI 生成过程需要有趣的加载动画，降低等待焦虑
- **家长可控**：所有设置和敏感操作需家长验证
- **分层复用**：组件、业务逻辑、AI 能力分层；当前不做 Taro/小程序，未来多端复用同一套 API
- **体验优先**：每个版本以家庭试玩和黄金 Prompt 集验收，不以“功能做完”作为完成标准
- **可迁移**：数据模型、存储、配置为 V5.1 云端留缝，但不提前实现云端

## 验收标准

验收标准必须可测试、无歧义。不同阶段采用不同验收方式：

- **V3.x 内在品质**：`typecheck` + `build` + 核心回归测试全绿；`api/` 与 `server/` 契约一致；文档与代码一致；性能/成本基线记录在案。
- **V4.x 体验**：黄金 Prompt 集可玩率/成功率达到目标；家庭试玩满意度连续两版达标；无破版、无作品丢失。
- **V5.x 平台**：儿童安全/隐私自检通过；限流/配额/成本测试通过；跨设备同步与迁移成功。
- **V6.x 社区**：亲友圈/公开社区 UAT 通过；审核/举报流程可运转；违规内容抽检通过。

验收失败后自动修复问题并重新验收，必要时更新对应版本的 UAT 文档补充测试用例。
